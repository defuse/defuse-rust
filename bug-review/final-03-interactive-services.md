# Security Review: Interactive Services (Final Pre-Deployment)

Reviewer: Claude Opus 4.6
Date: 2026-02-19
Scope: x86 assembler, big number calculator, HTML sanitizer, checksums, TRENT, password generator, vim highlighting

## Verdict: No showstopper issues found.

All seven areas reviewed appear safe for production deployment. Below is a summary of the analysis for each area, followed by minor observations that are NOT showstoppers.

---

## Area-by-Area Analysis

### 1. x86 Assembler (`src/libs/x86_assembler/`)

**Command injection via gcc/objdump:** NOT VULNERABLE. User input is written to a temp file (`code.s`), never interpolated into command arguments. `Command::new("gcc")` with `.arg()` calls avoids shell interpretation entirely. File paths are constructed from `TempDir::new()` (random system-managed paths), not from user input.

**Preprocessor inclusion:** NOT VULNERABLE. Two independent defenses prevent C preprocessor execution: (1) lowercase `.s` extension (GCC only preprocesses `.S` uppercase), and (2) explicit `-x assembler` flag overrides extension-based detection. Even if one defense fails, the other catches it.

**Directive injection:** NOT VULNERABLE. The whitelist-based filter (`filter.rs`) removes known-safe directives, then rejects ANY remaining `.` character. This prevents `.include`, `.incbin`, `.fill`, `.space`, `.rept`, and all other GAS directives. The `SafeAsm` newtype ensures the executor cannot be called with unvalidated input.

**XSS via `|safe` in template:** NOT VULNERABLE. Three uses of `|safe`:
- `hex_zero_bold`: Constructed from objdump output (hex characters only), with a runtime `assert!` that `html_escape()` is a no-op before injecting `<b>00</b>` tags.
- `format_disassembly()`: Calls `html_escape::escape_text()` which performs full HTML escaping before rendering.
- `err`: Calls `format_error()` which runs through `html_escape::escape_text()`.

### 2. Big Number Calculator (`src/libs/big_number_calculator/`)

**Command injection via Ruby:** NOT VULNERABLE. Three independent defense layers:
1. **Character whitelist** (`filter.rs`): Only allows `0-9`, `a-f`, `A-F`, `r`, `x`, math operators, spaces, and parentheses. No semicolons, newlines, quotes, backticks, dollar signs, or other shell/Ruby metacharacters pass the filter.
2. **Grammar parser** (`grammar.pest` via pest): Full PEG grammar that only accepts valid arithmetic expressions. Rejects function calls (`exec(1)`), identifiers (`abc`), method calls (`1.class`), range operators (`1..10`), and all non-arithmetic constructs.
3. **Shell escaping** (`evaluator.rs`): Single-quote wrapping with proper escaping. Defense-in-depth only, since the whitelist already excludes all shell metacharacters.

Additionally, the Ruby process runs with `ulimit -t 10 -v 262144` (10s CPU, 256MB memory) and a tokio timeout with `kill_on_drop(true)`.

**XSS via `|safe` in template:** NOT VULNERABLE. The calculator output goes through a runtime `assert!` that `html_escape()` is a no-op on the Ruby output (line 112 in `mod.rs`). Since the input filter restricts output to digits, hex letters, `-`, `/`, `.`, space, `true`, `false`, this assertion should never fire. The only HTML injected is `<b>00</b>` for zero-bold, `<br />` for newlines, and a `<div style="text-align: right;">` wrapper -- all generated by the Rust code, not from user input.

### 3. HTML Sanitizer (`src/pages/services/html_sanitize.rs`, `src/libs/html_escape.rs`)

**XSS bypass:** NOT VULNERABLE. The `escape_text()` function performs HTML entity escaping (step 2) converting `&`, `<`, `>`, `"`, `'` to their entity equivalents. The `<br />` insertion (step 6) happens AFTER escaping, using only the literal string `"<br />\n"`. The `&nbsp;` insertions (steps 3-5) are also safe HTML entities.

**`|safe` usage:** The `source_html|safe` in the template renders syntax-highlighted PHP source code from a static file (`static/source/HtmlEscape.php`) via vim -- not user input.

### 4. Checksums/Hashing (`src/pages/services/checksums.rs`)

**File upload handling:** Safe. File size is capped at 5MB (`MAX_FILE_SIZE`). File content is only used as input to hash functions -- never written to disk, never used as a filename, never interpreted as code. Hashing is done in `spawn_blocking` to avoid blocking the async runtime.

**No path traversal:** File uploads are processed purely in memory. The filename from the multipart form is only used for the `file_field` lookup key, not for filesystem operations.

**No resource exhaustion beyond the 5MB limit:** The hash computations are all fixed-time per byte of input. CPU-intensive work runs in a blocking thread.

### 5. TRENT (`src/pages/services/trent.rs`, `src/libs/trent.rs`)

**Randomness quality:** Uses `rand::rngs::OsRng` (kernel CSPRNG) for all random operations: password generation, random number selection, and random line selection. The `select_random_number` function uses 32 bytes of entropy with streaming modular reduction, providing uniform distribution with negligible bias.

**Path traversal in temp files:** NOT VULNERABLE. The `temp_path()` function validates that the hash parameter passes `is_sha256_hex()` (exactly 64 hex characters) before constructing the path. An `assert!` provides defense-in-depth. The path format is `/tmp/trent-{drawing_num}-{hash}` where both components are validated (i32 and hex string).

**XSS in template output:** NOT VULNERABLE. The TRENT template does NOT use `|safe` for any user-controlled content. All user inputs (`userprintout`, `printout`, `name`, `description`, form values) are rendered through Askama's default auto-escaping. The `userprintout` and `printout` are displayed inside `<textarea readonly>` elements which are inherently safe from XSS.

**SQL injection:** NOT VULNERABLE. All database queries use parameterized queries via sqlx's `.bind()`.

**TOCTOU on drawing completion:** Handled. The `UPDATE` query includes `AND complete = 0` to prevent concurrent double-completion.

### 6. Password Generator (`src/pages/software/passgen.rs`, `src/libs/passgen.rs`)

**Randomness quality:** Uses `OsRng` (kernel CSPRNG). Correct.

**Bias in generation:** NOT VULNERABLE. Uses rejection sampling with a minimal bit mask to achieve uniform distribution. For a 94-character ASCII set (mask=127), roughly 74% of random bytes are accepted -- no bias. The constant-time indexing via the `subtle` crate prevents timing side-channels.

**Iteration limit:** Has a `length * 128` iteration limit to prevent infinite loops from a broken RNG, which is astronomically unlikely to trigger under normal operation.

### 7. Vim Syntax Highlighting (`src/libs/vim_highlight.rs`)

**Command injection via vim:** NOT VULNERABLE for production use. The `file_type` and `color_scheme` fields have clear `SAFETY` doc comments stating they must only be set from hardcoded literals. All call sites in the codebase use hardcoded strings ("ruby", "php", "text", "c", "default"). The `set_vim_command()` method whitelist-validates to only "vim", "vi", or "gvim". User input is written to a temp file and passed as a file path argument, never interpolated into `-c` commands.

**Path traversal in cache:** NOT VULNERABLE. Cache paths are constructed from MD5 hashes of content + settings, resulting in predictable filenames like `string-{hash}.highlighted.html` in the configured cache directory. No user input reaches the cache path construction.

**XSS from vim output:** Acknowledged in the module's doc comment: "This SHOULD NOT be used on untrusted input, since there may be bugs in vim's HTML generation." However, in production, vim only highlights static source files and hardcoded strings -- never user-submitted content. This is acceptable.

## Minor Observations (NOT Showstoppers)

These are noted for completeness but do NOT need to be fixed before deployment:

1. **TRENT select_random_lines O(n^2):** Acknowledged in a TODO comment (line 533 of trent.rs). When selecting N lines without replacement from an N-line file, the rejection-sampling loop can take O(N^2) iterations. Capped at 1000 lines, so worst case is roughly 1M iterations -- noticeable but not a serious DoS since it only affects the drawing creator (authenticated by password).

2. **TRENT review_time not validated against dropdown values:** The `prereview` field accepts any u32, not just the dropdown options. A large value could cause timestamp arithmetic overflow. Not exploitable for security since instant (0) review is allowed anyway.

3. **Checksums page uses AI-generated hash implementations:** The file header warns "AI-generated implementations which HAVE NOT BEEN REVIEWED FOR SECURITY." For a hash display service (not security-critical operations), incorrect hashes would be a correctness bug, not a security vulnerability.
